# Post-deployment product corrections — local acceptance

Starting commit: `8b08e0f6e9ef79798c3829c073d8b36fccae0617`, on `main`.
No production settings, credentials, deployments, pushes or paid provider calls were used.

## Implemented behavior

- Recycle Bin previously protected executed runs indefinitely. Soft delete and restore still preserve identity/evidence; an authenticated personal owner or organization Owner can now explicitly purge a terminal, already-deleted run and its owned execution evidence. Restore is primary; permanent deletion is in a secondary danger disclosure and requires typing `DELETE`. Admin can restore but cannot purge; ordinary members cannot manage the bin. Seven child tables are removed before the parent, in one tenant transaction while the parent remains visible to FORCE RLS. Shared prepared uploads and immutable custom-agent/HR source revisions survive. Purging a research trial marks the surviving comparison incomplete, without rewriting other trials.
- Durable checkpoints require same-database atomic cleanup through `backend/migrations/checkpoint_purge.sql`. This optional operator-installed bridge has a dedicated NOLOGIN, non-superuser, non-BYPASSRLS owner, fixed qualified relations, restricted grants, active-actor/tenant/owner checks, exact thread FORCE RLS and the worker advisory lock. Application runtime receives only function EXECUTE. SQLite with separate PostgreSQL durable checkpoints, missing bridge, different database, unsupported non-ASCII legacy identifiers or an active worker fails closed. A persisted `durableCheckpoint` marker preserves this guard when runtime settings are turned off. Keep the bridge installed for historical checkpoints; pre-marker graph history also requires retaining its cleanup configuration. No production bridge was installed.
- Custom agents previously lacked a clear removal workflow. They now expose a confirmed Archive action that writes an inactive immutable revision. Archived agents cannot start runs; previous executions retain their original revision/output. Existing configuration supports reactivation. No permanent custom-agent deletion is offered. Built-ins are protected by server APIs: orchestrator, research, data, analysis, summarizer, report, direct and web_search. The coordinator does not execute provider calls; web search remains unavailable.
- Organization invitations previously used a reusable hash with a one-time plaintext display. Managers now see persistent masked lifecycle history: ID, creation/creator, active/consumed/revoked state and use attribution. Owner/Admin can generate, copy a newly generated secret, revoke an unused code and generate a replacement. Replacement revokes the previous active code. Successful join atomically consumes the code; reuse and revoked codes are rejected. Secrets remain hashed, never stored in history. Existing hashes migrate to managed legacy one-time invites. There is no expiry TTL; active codes remain valid until use/revocation/replacement. Plaintext cannot be redisplayed after reload; masked history remains visible and replacement is available. Ordinary members cannot list/manage invitations.
- Last active Owner has no remove/demotion controls and sees “Transfer ownership before removing or changing this owner.” Owner alone changes IAM roles; Admin removes ordinary members only. Application modals replace native confirmation for removal and explain self-removal. Actor/target stay separate; removal immediately revokes HR responsibilities. IAM and HR authority remain separate. Server transitions serialize on the workspace (SQLite write lock/PostgreSQL row lock) and count active user identities, preventing concurrent removal of all owners.
- Readiness now uses Ready / Limited connectivity / Offline, with separate workspace-unavailable/loading states and expanded truthful backend/workspace/live-event details. REST remains usable when live updates are offline; unavailable workspace blocks workspace actions. No WebSocket success is fabricated.
- Research Lab begins with a visible new-experiment setup, Single/Fixed/Adaptive explanation and real benchmark selection; prior experiments occupy a separate history/empty state. Seven versioned synthetic benchmark cases are code/file-defined in `backend/database/benchmarks/research-v1.json`, not database seeds. The file was moved unchanged into the backend package so backend-only deployment contains it. Fixture provenance, original directives, fingerprints, final/raw/rendered output, routes/skips and intermediate stages remain preserved. Fixture results make no live quality superiority claim.
